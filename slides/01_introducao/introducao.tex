\begin{frame}
   \frametitle{História dos Sistemas UNIX}
   \begin{itemize}
      \item Unix foi desenvolvido pelo \textit{Bell Labs} logo após esse laboratório abandonar o projeto \textit{Multics}.
      \item Algumas decisões de projeto foram reaproveitadas do \textit{Multics}:
      \begin{itemize}
         \item Dispositivos como arquivos.
	 \item Interpretador de comandos como processo independente do \textit{kernel}.
      \end{itemize}
      \item O \textit{Bourne Shell} e a linguagem \textit{awk} foram incluídos na versão 7 do UNIX.
      \item Um foco forte na criação de ferramentas para processamento textual.
      \item Padrão POSIX.
   \end{itemize}
\end{frame}

\begin{frame}
   \frametitle{Princípios Para Ferramentas de \textit{Software}}
   Os ambientes UNIX obedecem os seguintes princípios no desenvolvimento de suas ferramentas:
   \begin{itemize}
      \item Cada ferramenta deve oferecer apenas uma \textbf{funcionalidade} e implementá-la da melhor maneira.
      \item Processar \textbf{linhas de texto}, evitar dados binários.
      \item Aproveitar o poder das \textbf{expressões regulares}.
      \item Utilizar a \textbf{saída padrão} para troca de dados.
      \item Evitar \textbf{mensagens desnecessárias} no terminal.
      \item Utilizar para a saída o \textbf{mesmo formato} da entrada.
      \item Reutilizar programas \textbf{existentes}.
      \item Tente \textbf{generalizar} suas ferramentas.
   \end{itemize}
\end{frame}

\begin{frame}
   \frametitle{Linguagens de \textit{Scripting} versus Linguagens Compiladas}
   \begin{itemize}
      \item Programas escritos em linguagens compiladas são traduzidos do seu \textbf{código fonte} original para o \textbf{código objeto} da máquina alvo.
      \item A vantagem é que são programas eficientes, a desvantagem é que atuam em baixo nível.
      \item Exemplo da desvantagem: escrever em C um programa que copie todos arquivos de um diretório para outro.
      \item Linguagens de \textit{script} são interpretadas, um \textbf{interpretador} lê cada linha do \textit{script} e usa funções internas para executá-las.
   \end{itemize}
\end{frame}

   \begin{frame}
      \frametitle{O que é o \textit{Shell}?}
      \begin{itemize}
         \item O \textit{shell} é simplesmente o programa que lê o comando que você teclou e o converte em uma forma mais simplificada e legível ao sistema operacional (\textit{kernel}). 
         \item Também fornece uma \textbf{linguagem} para organizar uma sequência de comandos em  arquivos de texto chamados \textit{scripts}, permitindo a automização de tarefas administrativas. 
	      \item Um dos grandes diferenciais é permitir invocar programas feitos em outras linguagens sem dificuldade.
	      \item A troca de dados entre programas é feita em formato de linhas de \textbf{texto simples}.
      \end{itemize}
   \end{frame}

   \begin{frame}
      \frametitle{Tarefas do \textit{Shell}}
      \begin{itemize}
         \item Exame da linha de comandos recebida.
         \item Atribuição e substituição de variáveis.
         \item Resolução de redirecionamentos.
         \item Substituição de metacaracteres.
         \item Criação de processos filhos para executar comandos.
      \end{itemize}
   \end{frame}

   \begin{frame}
      \frametitle{Principais versões do \textit{Shell}}
      \begin{itemize}
         \item Bourne Shell (sh).
         \item Bourne Again Shell (bash).
         \item Korn Shell (ksh).
         \item C Shell (csh).
         \item Z Shell (zsh).
      \end{itemize}
   \end{frame}

\begin{frame}
   \frametitle{Por que usar \textit{Shell}?}
   \begin{itemize}
      \item É mais fácil lidar com arquivos e diretórios em \textit{shell}, assim iniciar ou finalizar outros programas.
      \item O desempenho costuma ser pior, mas o tempo de desenvolvimento é bem menor do que em linguagens compiladas.
      \item Simplicidade.
      \item Portabilidade.
      \item Facilidade de desenvolvimento.
   \end{itemize}
\end{frame}

\begin{frame}
   \frametitle{OFF-TOPIC: Como Usar o SSH/SCP}
   \begin{itemize}
      \item O SSH é um protocolo para \textit{login} remoto que utiliza criptografia para proteger a troca de informações.
      \item O comando \textit{ssh} no Linux implementa o lado cliente do protocolo.	
      \item O protocolo SSH também pode ser usado para transferir arquivos, não só enviar comandos.
      \item O comando \textit{scp} permite a cópia de arquivo entre cliente e servidor e também entre dois servidores remotos.
      \item A vantagem é que toda a comunicação é criptografada e protegida por senha.
   \end{itemize}
\end{frame}

\begin{frame}
   \frametitle{Autenticação no Servidor SSH}
   Utilizar senhas tem seus problemas:
   \begin{itemize}
      \item Uma senha complexa é fácil de esquecer.
      \item O usuários acabam escolhendo senhas fáceis, que podem ser descobertas e causar problemas de segurança.
      \item Uma solução melhor e amplamente utilizada nas nuvens é o uso de um arquivo de identificação chamado \textbf{chave}.
      \item Cada arquivo de chave está associado com um usuário no servidor.
      \item O usuário deve ter cuidado para proteger sua chave, qualquer que tiver acesso à ela poderiá acessar o servidor.
   \end{itemize}
   A solução mais segura é exigir que o usuário forneça uma \textbf{senha e a chave} toda vez que for logar. Mas deixamos para aprender isso mais adiante no curso.
\end{frame}

\begin{frame}[fragile]

      $ ssh -i joaomarcelo.pem joaomarcelo@servidor.example.com

      \item O servidor remoto é \textit{servidor.example.com}.
      \item O usuário \textit{joaomarcelo} deve existir no servidor remoto e estar configurado para permitir o acesso via chave.

   Em nuvens computacionais (AWS, Azure, Google, etc) o \textit{login} é feito por arquivo de chaves.
   \begin{block}{Lembrete}
   A chave tem que ter permissões de acesso apenas para o usuário local. Portanto, confirme:
   \begin{minted}[fontsize=\scriptsize]{bash}
      $ chmod 0600 joaomarcelo.pem
   \end{minted}
   \end{block}

\begin{frame}[fragile]
   \frametitle{O Problema de Digitar Tudo Toda Vez}
   Repetir a linha inteira a cada acesso é cansativo e propenso a erro:
   \begin{minted}[fontsize=\scriptsize]{bash}
      $ ssh -i ~/.ssh/joaomarcelo.pem joaomarcelo@servidor.example.com
      $ scp -i ~/.ssh/joaomarcelo.pem teste.txt joaomarcelo@servidor.example.com:
   \end{minted}
   \begin{itemize}
      \item Você precisa lembrar o caminho da chave, o nome do usuário e o endereço do servidor.
      \item Se a chave for protegida por \textit{passphrase}, ela é pedida a cada comando.
   \end{itemize}
   O Ubuntu (e qualquer Linux) oferece duas ferramentas para resolver isso:
   \begin{itemize}
      \item O \textbf{\textit{ssh-agent}}: guarda a chave destravada na memória durante a sessão.
      \item O arquivo \textbf{\textit{\textasciitilde/.ssh/config}}: dá um apelido para cada servidor.
   \end{itemize}
\end{frame}

\begin{frame}[fragile]
   \frametitle{Organizando o Diretório \textit{\textasciitilde/.ssh}}
   Por convenção, chaves e configurações ficam em \textit{\textasciitilde/.ssh}:
   \begin{minted}[fontsize=\scriptsize]{bash}
      $ mkdir -p ~/.ssh
      $ mv joaomarcelo.pem ~/.ssh/
      $ chmod 700 ~/.ssh
      $ chmod 600 ~/.ssh/joaomarcelo.pem
   \end{minted}
   \begin{itemize}
      \item \mintinline{bash}{chmod 700} no diretório: só o dono entra e lista.
      \item \mintinline{bash}{chmod 600} na chave: só o dono lê e escreve.
      \item O cliente \textit{ssh} \textbf{recusa} usar uma chave com permissões abertas demais, com a mensagem \textit{UNPROTECTED PRIVATE KEY FILE}.
   \end{itemize}
   Se ainda não tem uma chave própria, você mesmo pode gerar um par:
   \begin{minted}[fontsize=\scriptsize]{bash}
      $ ssh-keygen -t ed25519 -f ~/.ssh/id_ed25519 -C "seu.email@ufc.br"
   \end{minted}
\end{frame}

\begin{frame}[fragile]
   \frametitle{Ativando o \textit{ssh-agent} no Ubuntu}
   O \textit{ssh-agent} é um processo que mantém suas chaves destravadas na memória.
   \begin{block}{Verificando se já existe um agente ativo}
      \begin{minted}[fontsize=\scriptsize]{bash}
         $ echo $SSH_AUTH_SOCK
         /run/user/1000/keyring/ssh
      \end{minted}
   \end{block}
   \begin{itemize}
      \item No \textbf{Ubuntu Desktop}, a sessão gráfica já inicia um agente automaticamente. Se a variável acima tem um valor, não precisa fazer mais nada.
      \item Em um \textbf{servidor}, dentro do \textbf{WSL} ou numa sessão sem interface gráfica, a variável costuma vir \textbf{vazia}: é preciso iniciar o agente na mão.
   \end{itemize}
   \begin{block}{Iniciando o agente manualmente}
      \begin{minted}[fontsize=\scriptsize]{bash}
         $ eval "$(ssh-agent -s)"
         Agent pid 3412
      \end{minted}
   \end{block}
\end{frame}

\begin{frame}[fragile]
   \frametitle{Por que \texttt{eval}?}
   \begin{minted}[fontsize=\scriptsize]{bash}
      $ ssh-agent -s
      SSH_AUTH_SOCK=/tmp/ssh-XXbK2p/agent.3411; export SSH_AUTH_SOCK;
      SSH_AGENT_PID=3412; export SSH_AGENT_PID;
      echo Agent pid 3412;
   \end{minted}
   \begin{itemize}
      \item O comando \mintinline{bash}{ssh-agent -s} não configura nada: ele apenas \textbf{imprime} os comandos de \textit{shell} necessários.
      \item O \mintinline{bash}{eval} pega essa saída e a \textbf{executa} no \textit{shell} atual, definindo as variáveis de ambiente.
      \item Sem o \mintinline{bash}{eval}, o agente até sobe, mas o cliente \textit{ssh} não sabe como falar com ele.
      \item Voltaremos a esse comando quando estudarmos substituição de comandos e variáveis de ambiente.
   \end{itemize}
\end{frame}

\begin{frame}[fragile]
   \frametitle{Carregando a Chave com \textit{ssh-add}}
   \begin{minted}[fontsize=\scriptsize]{bash}
      $ ssh-add ~/.ssh/joaomarcelo.pem
      Enter passphrase for /home/aluno/.ssh/joaomarcelo.pem:
      Identity added: /home/aluno/.ssh/joaomarcelo.pem
   \end{minted}
   \begin{itemize}
      \item A \textit{passphrase} é pedida \textbf{uma única vez}. A partir daí o agente responde pelas conexões.
      \item Se a chave não tiver \textit{passphrase}, ela é adicionada direto, sem perguntar nada.
   \end{itemize}
   \begin{block}{Comandos úteis}
      \begin{minted}[fontsize=\scriptsize]{bash}
         $ ssh-add -l              # lista as chaves carregadas
         $ ssh-add -t 3600 chave   # carrega, mas expira em 1 hora
         $ ssh-add -d chave        # remove uma chave do agente
         $ ssh-add -D              # remove todas as chaves
      \end{minted}
   \end{block}
   O agente morre junto com a sessão: ao reiniciar a máquina, é preciso carregar a chave de novo.
\end{frame}

\begin{frame}[fragile]
   \frametitle{O Arquivo \textit{\textasciitilde/.ssh/config}}
   Um arquivo de texto onde você guarda as opções de conexão de cada servidor:
   \begin{minted}[fontsize=\scriptsize]{bash}
      $ nano ~/.ssh/config
      $ chmod 600 ~/.ssh/config
   \end{minted}
   \begin{minted}[fontsize=\scriptsize]{apacheconf}
      # Servidor da disciplina
      Host disciplina
          HostName servidor.example.com
          User joaomarcelo
          IdentityFile ~/.ssh/joaomarcelo.pem
          IdentitiesOnly yes
          AddKeysToAgent yes
   \end{minted}
   \begin{itemize}
      \item A indentação é opcional, serve apenas para facilitar a leitura.
      \item Linhas iniciadas por \texttt{\#} são comentários.
   \end{itemize}
\end{frame}

\begin{frame}[fragile]
   \frametitle{Significado das Diretivas}
   \begin{itemize}
      \item \textbf{Host} --- o apelido que você vai digitar. Vale qualquer nome curto.
      \item \textbf{HostName} --- o endereço real (nome ou IP) do servidor.
      \item \textbf{User} --- o usuário remoto, dispensando o \mintinline{bash}{usuario@}.
      \item \textbf{IdentityFile} --- o caminho da chave, dispensando a opção \mintinline{bash}{-i}.
      \item \textbf{IdentitiesOnly yes} --- usa \textbf{apenas} a chave indicada. Sem isso, o \textit{ssh} tenta todas as chaves do agente e o servidor pode recusar a conexão por excesso de tentativas.
      \item \textbf{AddKeysToAgent yes} --- carrega a chave no agente automaticamente na primeira conexão, poupando o \textit{ssh-add}.
   \end{itemize}
   Outras diretivas comuns: \mintinline{bash}{Port} (porta diferente de 22) e \mintinline{bash}{ServerAliveInterval 60} (evita que a conexão caia por inatividade).
\end{frame}
